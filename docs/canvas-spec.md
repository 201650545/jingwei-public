## 视觉

| 项 | 值 |
|---|---|
| 背景 | `#000` |
| 网格 | 点阵 `radial-gradient(rgba(255,255,255,.12) 1px)`，间距 24px（v3.2 建议 28~32px 极淡），随平移/缩放同步；缩到较小时进一步减淡 |
| 节点 | 背景 `#000`，1px 描边 `rgba(255,255,255,.26)`，圆角 2~3px |
| 节点 hover / 拖拽 | 描边提到 `rgba(255,255,255,.62)` / `#fff` |
| 连线 | 1px `rgba(255,255,255,.25)`，贝塞尔曲线，**无箭头、无大圆盘、无流动粒子**；端点可用极小圆点 |
| 静态文字 | 标题 `#fff` 15~16px/600（**标题是节点第一视觉重心，不与耗时争抢空间**） |
| 角色标签 | 顶部左侧 10px 等宽弱白，如 `PRODUCE / 03`、`00 / INTAKE`、`OUTPUT / FINAL` |
| 弱化元信息 | 模型名、产物类型（`MD / HTML / PNG / JSON`）降到 10px、约 42% 白，**不用彩色图标或装饰性胶囊** |
| **完成态语义色** | `rgb(80,255,150)`：**只属于 `status === 'done'`** |

**色相纪律（v3.2）**：**只允许一种色相**——完成态绿 `rgb(80,255,150)`，除它之外不得出现任何色相（蓝/黄/红/hsl/渐变）。
**绿色的唯一入口是「执行完成」**：不得用于 `review: pass`、`delivery: ready`、`humanReview: accepted`。
**不要把整张节点卡染绿、不要绿色大边框、不要绿色沿连线传播**——用「12px × 2px 绿色短线 + 「执行完成」文字」表达即可。
**核查未过 / 交付受阻 / 人工退回**一律用**白底黑字反相签**（像印在档案上的结论，不是错误警报），**不用红**；反相签高度约 20px，紧凑，无圆角或仅 1px 圆角。
**作用域**：以上纪律**只约束画布**；成果页（output 产出的独立 HTML）可用颜色表达 PASS/FAIL —— 判据是「这个颜色会不会让人误以为『画布上这个节点完成了』」。

**形状与光效**：允许 `box-shadow` 发光，但只允许用于 done 态；其余状态禁止阴影。圆角 ≤ 4px，**唯一例外是模型面板的圆形悬浮按钮 `.mp-fab`（50%）**。仍禁止 emoji、图标库。

## 状态表达：四条独立的轴（v3.2 核心）

**执行状态、核查结论、人工验收、交付状态是四条独立的轴，不能合并成一条「好坏状态」。**
尤其不能从 `status: done` 推断 `review: pass`，也不能从 `review: pass` 推断 `delivery: ready`。

| 数据状态 | 视觉表达 |
|---|---|
| `status: idle` | 灰「待执行」 |
| `status: running` | 白色虚线边界 +「运行中」 |
| `status: done` | **绿色短线 +「执行完成」**（绿只归它） |
| `status: failed` | 灰白「执行失败」，**无绿色** |
| `review: pass` | 灰白「核查通过」，**不加绿** |
| `review: fail` | **反相签「核查未过」** |
| `review: pending` | 弱白「待核查」 |
| `review: unknown` | 弱白「结论未知」 |
| `humanReview: accepted` | 白色文字「人工已验收」 |
| `humanReview: rejected` | 反相签「人工退回」 |
| `humanReview: pending` | 弱白「待验收」 |
| `delivery: ready` | 「可交付」 |
| `delivery: blocked` | 「交付受阻」（黑白强调，**不挪用**执行失败/核查失败的标签） |
| `delivery: failed` | 「交付失败」 |

`humanReview` 主要放在**具备人工验收意义**的节点上（尤其最终 output），不必让所有中间节点都出现多条审查信息。

## 节点内部的三层信息（v3.2）

```
① 做什么      顶部角色标签（10px 等宽弱白）+ 标题（15~16px/600，最多两行）
② 执行到哪    中部执行状态：运行中 / 执行完成 + 耗时（10.5~11px 等宽）/ 执行失败
③ 结果与来源  底部 1px、约 12% 白的分隔线隔开：
              review 结论在这里；模型名、产物格式降到最弱
```

- **没有核查结论的节点，不要硬凑一行「未知」**——显示内容应与节点责任相符
- 节点可因长标题增高，但**状态变化不得改变高度**（否则连线与 fit 都要跟着重算）
- 整体字阶控制在**四档以内**，层级靠空间、字重与明度建立，不是不断加样式

## 首尾端点造型（v3.2）

**intake = 一张委托卡**（工作的起点）
- 左侧 2px 更显眼的白色短竖线；顶部 `00 / INTAKE`；下方是主要任务标题
- 可比普通节点稍宽稍高，视觉重心偏左；**不显示无意义的模型名或核查标签**
- 保持黑底灰白边，**不做大面积白底**
- 让人一眼明白：这是整张图的开端，不是另一个生产 Agent

**output = 一张最终作品的封签**（画面的终点）
- 双层细框的**局部**处理：最外圈弱白轮廓，内侧顶部用短水平线形成收束结构（**不需要两个完整粗边框**）
- 顶部 `OUTPUT / FINAL`，标题略大于普通节点；依次显示执行状态、**交付状态**、人工验收结果
- 产物格式放底部（`HTML DOCUMENT`），作为作品属性，不是巨大按钮
- **output 是画面终点，不是「成功」的视觉符号**——即使 execution 完成而 `delivery` 是 `blocked`，也必须保持端点造型并如实显示阻塞状态，**不能描成一枚绿色奖章**
- 双击依然进入原有产物预览

## 尺寸与间距（v3.2，缩放前世界坐标）

| 元素 | 建议规格 |
|---|---|
| 普通节点 | 216 × 124~144px |
| intake | 228 × 142px |
| output | 240 × 152px |
| merge | 176 × 92px |
| audit | 200 × 120px |
| 双列中心距 | 252px |
| 同层横向净间距 | 36px |
| 上下层净间距 | 72~88px |
| 普通节点内边距 | 水平 18px、垂直 15px |
| 圆角 | 2px |
| 默认网格 | 28~32px 极淡点阵 |

- 同一层级优先**双列**；更多并行节点展开为多行/多列，**不能为造型强行改依赖**
- **420px 右栏用同一套世界坐标布局 + fit 适配**，不改造成移动端卡片列表
- 首次 fit 的任务是交代整张图的结构；复杂 DAG 在窄栏里必然变小，**放大后才看得清的细节不该被塞进缩略视图**

## 连线（v3.2，GPT 第 3 轮 §一 4 / §五）

**只画真实依赖**：连线只来自图的 `edges`，**绝不从"视觉上挨着"推导**，
更不许自动生成 `v1 → p3` 这类并不存在的假边。

### 路由

- **跨波次长边必须绕行**：四路并行时 `v1 → merge` 不能从 v1 底部直接向下**贯穿 p3 / v3**。
  做法：走**两列之间的中央走线区**（`x = AXIS ± 18`）——源底部 → 让位到走线区 → 沿通道直下 → 落回目标顶部。
- **走线区车道错位**：多根长边各占一条车道（间距 ≤7px，落在 `AXIS ± 18` 内），
  **不提前汇合成一条**——那会看起来像共享依赖。
- **只挡住的才绕**：中间没有节点的长边（末波核查 → 收口）走直连，不硬绕。
- **锚点错开**：同一节点的多条出入线在节点边上分散开，不挤在同一个点。
- **坐标系只有一个**：锚点一律用 `positions` + `offsetWidth/offsetHeight` 算出的画布世界坐标，
  **绝不与 `getBoundingClientRect()` 混用**。

### 亮度与状态

| 状态 | 视觉 |
|---|---|
| 静态 | 1px、约 25% 白 |
| 已流转 | 约 62% 白 |
| 与选中节点相关 | 约 80% 白 |
| 运行中 | 虚线缓慢移动，周期约 2.8s |
| 端点 | 极小圆点（r=1.8）；**不加箭头、大圆盘、流动粒子** |

- **边状态不只看上游 `done`**：没有边级事件时用保守规则
  「上游完成 **且** 下游已经开始或结束」。
- **亮度表达流转，不表达核查结论**：下游核查失败，连接线也**不变绿、不变成功样式**。
- 绿色**绝不沿连线传播**（绿只属于「执行完成」那根短线）。

### 重算时机

- 首次节点真实尺寸测量完成后计算一次；
- 节点拖动、内容尺寸变化、重新排布、图结构变化时更新；
- 拖动中的路径更新**合并到 `requestAnimationFrame`**；
- 尺寸变化由 `ResizeObserver` 触发（观察器**不写尺寸**，不会自激重排）；
- **不要**因为每次状态文字变化就重排整图——只有几何尺寸真变了才重算。

## 预览（v3.2，GPT §六 第 6 行 + §错误六）

全屏遮罩 `#000`；顶部一行灰字「产物预览 · ESC 关闭」+ 节点名 + **产物路径 · 类型**（最弱一级）
+ **「在浏览器打开」** + ×。

| 产物类型 | 展示方式 |
|---|---|
| `html` | **sandbox iframe**（`sandbox="allow-scripts"`，刻意不给 `allow-same-origin`） |
| `md` / `markdown` | **文本类**渲染：markdown → HTML（标题/粗体/行内码/列表/引用/分隔线） |
| `png` 等图片 | 图片居中，**max 92%** |
| `json` | 等宽 `pre` + 美化 |
| `pdf` | iframe |
| **未知类型** | **安全回退**：按等宽 `pre` 显示文本，**不失效** |

**markdown 渲染必须转义**（2026-10-20 安全加固）：
- 正文里的 `<` `>` `&` 一律转义 ⇒ 产物里的 `<script>` / `<img onerror>` 不会变成可执行标签；
- **链接只放行 `http` / `https` / `mailto`**：`javascript:` / `data:` / `vbscript:`
  （含带空格、带控制字符的变体）一律**只留文字、不生成 href**；
- 外链固定带 `rel="noreferrer noopener"`。

> 预览页跑在**插件自己的同源上下文**里，产物又是 AI 生成的文本 ——
> 转义与协议白名单是防线，不是锦上添花。

## 动效（v3.2：极少）

| 场景 | 动效与时长 |
|---|---|
| hover 节点 | 边框明度过渡 120ms |
| 选中节点 | 白色外轮廓立即出现，**不做缩放** |
| 运行中 | 虚线缓慢移动，周期约 2.8s；**只动连线上的虚线**，不让整卡呼吸、不闪文字 |
| 执行完成 | 绿色短线一次性出现 120ms；**不放烟花、不弹跳、不闪绿光** |
| 节点菜单 / 预览打开 | 透明度渐入 120ms / 160~180ms |
| F/0 fit | 平滑移动约 300ms |
| 节点拖动 | 直接跟手，0ms 延迟 |

- 核查未过、交付受阻**不震动不闪烁**——它们是需要阅读的结论，不是需要立刻消除的通知
- 轮询只更新变化的节点与连线，**不让整张画布重新入场**，正在拖动的节点尤其不能跳位
- 所有非必要动画服从 `prefers-reduced-motion`；拖动/平移/滚轮缩放**不加惯性**

## 六个最容易做错的地方（v3.2）

1. **把绿色变成「通过」的颜色**（最高风险）——一旦给 `review: pass` / `delivery: ready` / `humanReview: accepted` 也加绿，读者就分不清绿代表"执行结束"还是"成果合格"。**解法不是调深浅，是从渲染规则上限定绿色的唯一入口。**
2. **把 `role` 当 `kind` 用**——`role` 描述节点在编排中的职责；动作许可由 `kind`/现有规则决定。不能因为叫 output 就禁预览，也不能因为不是 merge 就默认可删。**四项菜单的动作与禁用条件、Host 校验边界必须保留。**
3. **为了画面整齐重排用户拖过的节点**——`view.json` 里的位置是用户的明确意图，**始终优先**。新布局只负责没有位置的新节点，不能在 R 重读/轮询/每次打开时重排全部。节点加宽后旧坐标可能局部重叠——**不能靠悄悄覆盖已保存位置解决**。
4. **节点高度变了、线却没更新**——新增状态行后节点内容多一行，仍用旧尺寸算连接端点就会线插进节点、曲线断开、fit 裁切。**做法：状态区预留稳定高度，尺寸变化后重算连线与 fit 边界。**
5. **把画布升级成仪表盘**——不要加常驻统计头、阶段导航条、图例、Inspector、百分比进度环、独立交付面板。**详细产物交给双击预览，不常用动作留在原菜单里。**
6. **忽略字段兼容**——`normalize()` 只保留它认识的字段。`role`/`review`/`humanReview`/`graph.delivery` 若没被保留，新视觉写好了也显示不出语义。**（2026-10-20 实测：`review`/`humanReview`/`delivery` 确实丢了，已修）**

## 交互（v3.1 已有，保留）

| 操作 | 行为 |
|---|---|
| 拖节点 | 移动节点；连线跟随；不改变视图 |
| 拖空白 | 平移画布 |
| 滚轮 | 以光标为锚点缩放，0.25～3 |
| 双击空白 | fit |
| 双击节点 | **不触发** fit（节点上的双击被忽略） |
| `F` / `0` | fit |
| `R` | 重新读 `index.json` → latest manifest，静默替换 |
| 窗口/面板尺寸变化 | 未手动平移缩放时自动 fit；否则只重绘连线 |

- 拖动阈值 2px；热键只在画布有布局且未被隐藏时响应（`display:none` / `hidden` / `inert` 的保活实例不响应）
- `R` 请求带递增序号，旧响应不会覆盖新数据
- 单击节点 = 选中；`⋯` = 四项菜单（重跑这一路 / 查看产物 / 复制模型名 / 删除节点）；Enter 重跑；双击预览；Esc 逐层关闭

**产物预览**：全屏遮罩 `#000`；顶部一行灰字「节点名 · Esc」+ **「在浏览器打开」**（v3.1 新增，调 `POST /jingwei/actions/open-external`）+ ×。
json/text 用等宽 pre，html 用 **sandbox iframe**（`sandbox="allow-scripts"`，**刻意不给 `allow-same-origin`** —— 脚本能跑但读不到父页面/localStorage、发不了 cookie、导航不了父页；**不给** allow-popups/allow-forms/allow-top-navigation），图片居中 max 92%。点遮罩空白或 Esc 关闭。

## 布局（v3.2）

**纵向主轴 + DAG 拓扑分层**（GPT-6 Sol《设计说明》§1.1 原文口径，2026-10-20 修正）：

- 图谱沿一条隐形的**纵向主轴**展开：**开始（intake）与结束（output）落在主轴上**。
- 中间的**生产、核查阶段向左右展开**（同一层级优先**双列**，双列中心距 252px）；
  **合并与终审重新收束**回主轴。
- 层级按**真实依赖关系**计算（拓扑层级），**不是按节点数组顺序排列**。
  典型阅读路径 `intake → produce → verify → merge → audit → output`。
- ⚠️ **`dagRank`（逻辑层级）≠ `visualRow`（视觉行）**（GPT 第 3 轮 §④）：
  逻辑层级由最长依赖路径算出，表达真实先后约束；视觉行由列数与单元编排算出，表达屏幕摆放。
  四路并行时 `p1` 与 `p3` 的 `dagRank` 相同却落在**不同的视觉行**——这是二维排版的代价，不是 DAG 变了。
- **核查节点紧跟它所核查的那一路生产者的正下方**（净间距 72~88px），
  否则多路并行时看不出「这一路的核查是哪一路」。
- **单元是布局策略，不是 DAG 数据结构**（GPT 第 3 轮 §⑤ 第三硬条件）：
  一个生产节点 + 它下游**唯一**的核查节点组成一个纵向视觉单元；
  一个核查依赖**多个**生产者、或一个生产者挂了**多条**核查 ⇒ **不拼单元**，
  核查自成单元走通用拓扑排布。**绝不能把共享核查硬挂到某个生产者头上**——那会画出并不存在的依赖。
- 同一层级的单元按**波次**排布：每波最多两个单元；
  下一波的顶部 = 上一波左右两个单元中**较低的那个底部** + 净间距（保证两列顶部对齐、不逐渐错乱）。
- 自动排布**只负责没有保存位置的节点**；`view.json` 里的坐标是用户的明确意图，**始终优先**。
- 排布尺寸取 **DOM 实测**（节点会因长标题长高），不用写死的数；尺寸变化后重算连线与 fit 边界。

### 旧版式坐标的迁移（GPT 第 3 轮 §⑦）

**默认保留所有已保存坐标**，只做三件事，**绝不擅自平移或缩放旧 x 坐标**：

1. `view.json` 写入 `layoutVersion`（当前 `3.2`）。**缺版本标记只判「版本未知」**，不武断认定是旧版式。
2. 加载后用节点真实矩形检测**实际重叠**；无冲突就不提示。
3. 检测到冲突时给一个**不阻断操作**的提示条：`[保留当前布局] [按新版式重排]`，重排后可撤销；
   同一份布局 + 同一布局版本下选过「保留」就不再重复打扰。

> 自动猜测旧版式来源，长期看比一次明确的重排更危险。

> ⚠️ 2026-10-20 修正记录：v3.1/v3.2 初稿把布局记成「语义角色分列、x = column × 240」，
> 那是**旧代码的实现**，不是 GPT 的设计意图，已按《设计说明》§1.1 改回纵向主轴分层。
